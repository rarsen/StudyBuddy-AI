# 4. Thesis plan

## 4.1 Working title

*Private, Offline Exam Preparation with Locally Run Language Models: Generating Grounded Practice Questions on Consumer Laptops*

## 4.2 Problem statement

Students mostly use study techniques that don't work well, such as re-reading and highlighting. They skip practice testing and spaced repetition because making practice material takes too long.

Cloud LLMs can generate that material, but they cost privacy, money and a network connection. Small open-weight LLMs can now run on student laptops. **No one has shown whether they produce practice material good enough, fast enough, on ordinary laptop hardware.**

## 4.3 Research questions and hypotheses

- **RQ1 (quality).** How do quizzes and flashcards generated by local 4–9B models compare with those from a cloud model, judged by human raters and by automatic checks?
  - *H1:* the local 8–9B model is no worse than the cloud model on correctness and groundedness, within a margin fixed before the evaluation.
  - *H1b:* the local 4B model is measurably worse, but by a limited amount.
- **RQ2 (performance).** How long does generation take on Apple Silicon laptops, and how much memory and energy does it use? Is that acceptable for this workflow?
  - *H2:* on a base M-series Mac, a 10-question quiz from one document section finishes within N minutes. Chat shows its first token within T seconds. Set N and T from a pilot run before the evaluation.
- **RQ3 (optional, techniques).** Which simple technique improves small-model output most?
  - The candidates:
    - forcing output to match a JSON schema;
    - choosing or sizing the source passage differently;
    - adding a self-check step.
  - *H3:* forcing a JSON schema brings invalid output to about 0%, with almost no added latency.

## 4.4 Contributions

1. A study assistant for the web and macOS that shares one codebase. A single setting switches it between cloud and local models.
2. A pipeline that turns lecture PDFs into quizzes and flashcards with page citations, scheduled with FSRS (a spaced-repetition algorithm).
3. A measured comparison of local and cloud models for generating practice material, covering quality, latency, memory, energy and cost.
4. A reproducible evaluation setup (`eval/`) and a dataset of rated questions.

## 4.5 Evaluation design

**Corpus**
- 6–10 openly licensed, lecture-style documents covering 3–4 subjects.
- Sources: chapters of OpenStax textbooks (CC BY 4.0) and MIT OpenCourseWare notes (CC BY-NC-SA 4.0).
- Record the source, license and page range of each document.

**Conditions**

| Id | Model | Where it runs |
|---|---|---|
| L-4B | ~4B, 4-bit (default for 8 GB Macs) | Mac, llama.cpp with Metal |
| L-9B | 8–9B, 4-bit (for Macs with 16 GB or more) | Mac, llama.cpp with Metal |
| C | The web edition's current cloud model | OpenAI API |
| (optional) L-alt | A model from another family (e.g. Gemma 4 E4B) | Mac |

**Generation protocol**
- Every condition uses the same prompts, JSON schema, source passages and settings.
- Generate 20 items per document per condition, about 600 items in total.
- Use temperature 0, or fixed random seeds.

**Automatic metrics**
- **Validity rate:** share of outputs that are valid JSON matching the schema, with and without schema forcing (RQ3).
- **Groundedness:** is the correct answer supported by the cited passage?
  - A judge model checks this. It must come from a *different model family* than every tested model.
  - Validate the judge against about 100 human-labeled items, using Cohen's κ (an agreement statistic).
- **Repetition:** rate of duplicate and near-duplicate questions, and how much of the source text the questions cover.
- **Difficulty:** distribution of difficulty and Bloom's-taxonomy level, as judged by the same model.

**Human rating**
- 3 raters (classmates or TAs). They don't know which model produced an item, and items appear in random order.
- About 150 items, balanced across conditions.
- Each item is rated 1–5 on:
  - correctness;
  - relevance and importance;
  - clarity;
  - how plausible the wrong answer options are;
  - whether the difficulty fits.
- Report how much raters agree, using Krippendorff's α.

**Performance** (on 2–3 Macs, ideally including an 8 GB base model)
- **Speed:** time per quiz and per flashcard batch; time to first token and tokens per second, for chat and for generation.
- **Prompt length:** how prompt-processing speed changes with prompt length.
- **Cold start:** time from app launch to a usable UI to the first token, and model load time when not cached vs cached.
- **Memory:** peak and steady memory per process (define the exact metric used).
- **Energy:** joules per quiz, measured with `sudo powermetrics`, and battery drain over a scripted 30–60 minute session.
- **Disk:** app size, model sizes, and database growth per 100 ingested pages.

**Cost**
- Cloud: cost per 1,000 items, from measured token counts times the price list current at the time of writing.
- Local: energy used times the electricity price. Each extra item costs the developer nothing.

**Optional user study**
- 10–15 adult students use the app for a week before an exam.
- Measure usability with SUS (System Usability Scale), task success, how useful they found it, and how fast it felt compared with how fast it was.
- This is exploratory only, so make no claims about learning gains.

**Statistics**
- Report 95% confidence intervals (Wilson or bootstrap).
- Compare conditions on the same source passages with paired tests:
  - Wilcoxon signed-rank for ratings and latency;
  - McNemar for yes/no outcomes.
- Report effect sizes.
- Fix the "no worse than" margin for H1 in advance.
- Correct for multiple comparisons with Holm–Bonferroni.

**Controls**
- Pin the llama.cpp version, and record the model files' hashes and the macOS version.
- Run on AC power with nothing else running.
- Let the machine cool down between runs.
- Discard 3 warm-up runs, repeat each measurement at least 5 times, and randomize the order.

**Threats to validity**
- **Raters:** classmates are few and not experts. Mitigation: a written rubric and a calibration round.
- **Judge bias:** the judge model may be biased. Mitigation: a different model family, randomized order, and validation against humans.
- **Hardware:** only a few devices are tested. Mitigation: report their specs, and include at least one Mac not used during development.
- **Subjects:** the corpus may not represent every subject. Mitigation: report results per subject.
- **Model churn:** models change quickly. Mitigation: freeze versions and date the results.

## 4.6 Scope and non-goals

- **In scope:** English; web + macOS on Apple Silicon; multiple-choice quizzes and flashcards; chat with citations; FSRS scheduling.
- **Out of scope:**
  - model training or fine-tuning;
  - Windows/Linux;
  - languages other than English;
  - grading open-ended answers;
  - agents and tools;
  - syncing across devices.

See [future work](05-future-work.md).

## 4.8 Metrics summary

| Area | Metric |
|---|---|
| Quality | Human rubric scores (1–5); groundedness rate; validity rate; duplicates; difficulty distribution |
| Agreement | Krippendorff's α between raters; Cohen's κ between judge model and humans |
| Latency | Time per quiz; time to first token (median and 95th percentile); prompt-processing and generation speed in tokens/s; cold start; model load time |
| Resources | Peak and steady memory per process; disk footprint |
| Energy | Joules per quiz (`powermetrics`); battery drain per hour |
| Cost | Cloud cost per 1,000 items vs local energy cost |
| Usability (optional) | SUS score; task success; how fast it felt |
| Offline | No outgoing connections during an offline session |
